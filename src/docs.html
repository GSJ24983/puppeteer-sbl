What changed in v0.5

  • No Rubric button for learners. Learners no longer see a Rubric button on the written answer, and their screen says 'Graded against 3 criteria', then '2 of 3 criteria met'. The coaching after each attempt still says what is missing. A scenario with "showRubric": true (a rubric-teaching one) still shows its rubric to everyone, open.
  • Send with Gmail or Outlook. 'Send by email' used a mailto: link, which needs a mail app set as the default - on many laptops there is none, so the browser asked which app to use, and choosing a browser opened a blank window. The send box now has Send with Gmail and Send with Outlook, which open the web mail page with the email written, plus Mail app (the old mailto) and Copy result. Each send button also copies the result, in case the mail page drops a long body.
  • Persona card. When a scenario carries an anchor, the ending has a 'Make my persona card' box above the send box. It opens the card page (https://gsj24983.github.io/swanubhava-play/card.html, or the deck's cardUrl) with a card code in the link. The engine works out three indicative bands - Noticing from the notice questions, Deciding from first picks on each decision, Saying it from the written criteria - and an overall band. The code carries the scenario, anchor number, bands, the learner's name and a random number that picks the persona; never choices or answers. The copied result also ends with the card code, so the card page can read a pasted result.
  • Open scenario file. On the Learner result tab. Pick a scenario file you exported and its scenario joins the JSON on the left, so a learner's result for it can be read. A .json file works as well.
  • The criteria are still inside every exported file, because grading runs in the learner's browser. Hiding the button stops a casual look, not someone reading the page source.

What changed in v0.4

  • Send to trainer is email and copy only. The WhatsApp button is gone. Learners send their result by email, copy it, or save their report.
  • A default address. When the deck sets no sendTo.email, 'Send by email' goes to swanubhava.by.gsj@gmail.com. The address shows under the buttons, so a learner whose mail app does not open can copy the result and send it themselves.
  • A consent line sits under the name field: 'By sending this, you agree that Gaurav Joshi sees your name, choices and written answers to give you feedback. Your name is optional.'
  • Older files with sendTo.whatsapp still load and play; the number is ignored.

What changed in v0.3

  • Trainee edition. This public Studio builds scenarios and trainee files. 'Export for trainees' removes the trainer-only fields (trainerNote, reveals, redFlags), so a curious learner can't read them in the page source. The trainer view, trainer export and class dashboard are in a separate edition.
  • Briefing and Rubric buttons. The old i and e buttons now say what they do, which matters most on a phone.
  • Send to trainer. The last screen asks for the learner's name and sends the result by email, or copies it. The learner can also save a personal report.

How this works

Left pane is content. The engine is frozen and lives inside this file. Preview runs the real engine in an iframe, so what you see is byte-for-byte what exports. Each export is one self-contained HTML file - offline, no dependencies, mail it to anyone.

Cmd/Ctrl + Enter re-runs the preview.

Scenario shape

{
  "deckTitle": "The Puppeteer",
  "sendTo": {"email":"swanubhava.by.gsj@gmail.com"},   // optional - where 'Send by email' goes. Left out, it goes to this address
  "scenarios": [{
    "id": "signoff",              // slug, appears in the session code
    "title": "...", "kicker": "...", "tag": "Product analysis",
    "anchor": "Challenges assumptions, reframes and holds a point of view",   // Swanubhava anchor this scenario trains, verbatim ('competency' still accepted)
    "pillar": "Boundary defining posture",   // optional - derived from the anchor when left out
    "behaviour": "pushes past the happy path",
    "meta": "6 min - 3 decisions", "thumb": "office",
    "blurb": "One sentence of tension.",
    "highlight": false,           // true = teal pill on the hub card
    "steps": ["Briefing","Decision","Write it down","Debrief"],
    "start": "brief",
    "nodes": { ... },
    "endings": { ... }
  }]
}

One scenario in the array and the hub is skipped - it opens straight into the run. Several, and you get a hub of cards.

Node types

narrative - sets the scene, one Continue button.

{"type":"narrative","step":0,"scene":"office","eyebrow":"Briefing",
 "title":"...","text":"...","media":[],"to":"n1"}

choice - the core mechanic. Each choice may carry a consequence screen before it routes on.

{"type":"choice","step":1,"scene":"office","prompt":"...",
 "gate": false,                  // true = wrong answers disable and retry, no advance
 "choices":[
   {"k":"A","label":"...","sub":"...","tag":"Signed as-is","chip":"Signed",
    "correct": false,            // only meaningful when gate:true
    "lesson":"coaching note shown on a gated wrong answer",
    "consequence":{"scene":"storm","title":"...","text":"...",
                   "lesson":"what this cost you","good":false},
    "to":"n2"}]}

A choice is the expert move when its consequence has "good": true; the others in that decision are traps. The learner's path diagram and report colour them that way.

multi - multi-select, rules-graded against correct indexes. No partial credit routing; it always continues to to, but the feedback names what was missed.

{"type":"multi","step":2,"scene":"matrix","prompt":"...",
 "options":[{"label":"...","sub":"...","why":"..."}],
 "correct":[0,1,3],
 "successNote":"...","missNote":"Before Friday you still need: ","to":"n3"}

Feedback names both kinds of slip: the ones they missed (after missNote) and the ones they picked that do not belong (after extraNote, default 'This one does not belong: '). Give any option an optional why - one short clause - and once any option has one, the feedback after Submit lists every option with what the learner did - picked it and it matters, missed it, picked it and it does not belong, rightly left out - and its why underneath. why is shown to learners; reveals is not.

evaluate - free text against a rubric. Criteria light up as they are met, and the grade arrives with coaching, not just a score. Routes to toPass or toFail.

{"type":"evaluate","step":3,"scene":"data",
 "speaker":"The delivery lead:",       // renders as in-character dialogue
 "question":"Write me the line...",    // use "prompt" instead for a plain instruction
 "criteria":[{
   "label":"Names the specific channel",
   "keywords":["sms","email","in-app","sends an sms", ...],
   "hint":"say which channel fires",   // short - used in the session summary
   "coach":"name the channel that actually fires - 'notify' is the word that let two teams build two different things"
 }],
 "pass":3,
 "coachLead":"To make this un-misreadable, ",
 "passNote":"...",
 "model":"When a refund is approved, the system sends...",
 "modelExplain":"This covers all three: it **names the channel**...",
 "redFlags":{"rule":"Any note that blames the customer fails, however good the rest is.",
             "phrases":["should have read","her responsibility"]},   // optional, NOT graded, trainer only
 "toPass":"good","toFail":"partial"}

redFlags (optional). A red line for the facilitator to talk about. It sits inside the folded rubric, under the criteria, so it appears only when you tap Rubric - the same reveal as the rubric. The engine never grades it: an answer containing these phrases scores exactly as it would without them. The validator only checks that the model answer does not contain one. The dashboard shows an answer that uses a phrase under 'Answers to discuss'. Red flags are trainer material, so the trainee export removes them.

Keywords: aim for 15-25 per criterion, mostly phrases. Single words either fire on everything or miss how people actually write. Include contractions, partial words (escalat catches the whole family), and the sideways phrasings. The validator complains below 8.

coach vs hint. hint is a fragment for the session summary. coach is a full sentence naming the mechanism - what breaks, when, and who pays. Missed criteria are joined into one paragraph after coachLead. This is where the teaching happens, so it is required.

model and modelExplain. Learners do not get a model answer button (v0.3): they see the model answer in their saved report, after the scenario ends. The validator grades the model against its own rubric and fails the scenario if it does not reach pass - so a rubric that cannot recognise a good answer never ships.

Attempts (v0.3). A learner gets 3 attempts at the written answer - set "tries" on the node or the deck to change it. After each graded attempt short of pass, they see how many rubric points they missed and the coaching, then choose Improve my answer (their text stays in the box) or Submit as is. After the last attempt the button just says Continue. The last submitted answer is the one that counts for the ending, the result code and the report. Grading shows a spinner, then a score pill and criteria revealing in sequence; set GRADE_DELAY = 0 in the exported file to make it instant.

The Briefing button - context on demand

Every choice, multi, evaluate and ending node carries a Briefing button. It opens what the learner has seen so far - briefing text and the consequences of their own decisions - so nobody has to scroll back while writing. The engine assembles it automatically; you only add context when you want to inject something extra.

"context":[{"label":"Policy note","text":"Refunds over 5000 need a second approver."}]

Grading is client-side keyword matching, deliberately. An API key in a shareable file is an exposed key. In a live session the rubric on screen is the artifact - you grade in the room.

Send to trainer and result codesv0.4

The last screen of every run has a 'Send your result to your trainer' box. The learner types a name if they want to - it is optional - and under the name field reads the consent line: 'By sending this, you agree that Gaurav Joshi sees your name, choices and written answers to give you feedback. Your name is optional.' Then they tap one of:

  • Send by email - opens their mail app with the result filled in, to sendTo.email, or to swanubhava.by.gsj@gmail.com when the deck sets none. The address is shown under the buttons.
  • Copy result - for anything else: Teams, a Google Form, a class channel, or when the mail app does not open.
  • Save my report - downloads a small page with their choices, what they wrote, which criteria they met and the ending. It is theirs to keep.

The ending screen does not show a separate session summary - the send box replaces it. The message it sends holds the plain summary and a result code starting PUP2:. The code carries every choice, every pick in a multi, the written answer, which criteria it met, the number of attempts and whether the model answer was used. It is encoded, not encrypted: anyone with the code can decode it, so treat it like the answer itself. The older PUP| line stays in the summary for your spreadsheets.

Learner resultv0.3

Open the Learner result tab above the preview, paste one learner's message - a whole WhatsApp or email message is fine - and press Show result. Keep their scenario loaded on the left. You see their path as a diagram, each choice, what they noticed and missed, their written answer and which criteria it met. It reads the first PUP2: code only; the class dashboard is in the trainer edition. Nothing here leaves your browser.

Anchor and pillar tagging

Scenarios are tagged to an anchor - one of the eight Swanubhava™ behavioural anchors, grouped in three pillars (Individual posture, Boundary defining posture, Collaboration posture) - and to the specific behaviour it trains. Put the anchor name in anchor, verbatim, sentence case: the tag groups sessions, so a changed capital letter becomes a new anchor in the spreadsheet. Older files that use competency still work. The pillar is filled in from the anchor; set pillar only to override it. The behaviour is where rubric criteria come from - it is already written as an observable behaviour, which is what a criterion has to be.

The tag shows on the hub card and the rail, and travels in every session summary and compact code, so a term of sessions pivots by anchor (and pillar) in a spreadsheet: which anchors a cohort is weak on, not just which scenarios they found hard.

Visual blocks

Narrative screens, consequences and endings take an optional blocks list. Each block sits above the text ("at":"top", the default) or below it ("at":"bottom"). They are drawn from the theme, so they need no files and work in both themes and offline.

"blocks":[
 {"type":"post","author":"Meera","handle":"@meera","meta":"Monday, 8:52 am",
  "text":"My father died twelve days ago...",
  "reply":{"from":"SkyBridge assistant","text":"You can book now...","link":"Fare policy"},
  "after":"Your bot told me to do exactly this.","stats":"1,800 reposts"},
 {"type":"people","title":"Three people matter this week",
  "people":[{"name":"Arjun","role":"Head of Customer Experience","lines":"..."}]},
 {"type":"image","alt":"what the picture shows","src":"","caption":"..."}
]

post is a social post, chat message or email, with an optional quoted reply styled like a screenshot. people is a cast card: initials, name, role, a line or two each. image shows the picture when src is an https link or a data:image URI, and a dashed 'Image to come' placeholder with the alt text when it is blank - so a planned visual is visible in a session before it exists. What a post or people block says is added to the Briefing panel, so learners can reread it while they write.

Line breaks

A \n inside any text field - narrative, consequence, lesson, prompt, verdict, the Briefing panel, trainer notes - shows as a line break, and \n\n as a blank line between paragraphs. Long lines still wrap. Use it for pointers and short paragraphs on long screens.

Formattingv0.3

Learner-facing text - narrative, consequence, lesson, decision and notice prompts, the speaker's question, the ending verdict, post text, the Briefing panel and modelExplain - takes four marks. Older modelExplain text written with <b> tags still shows in bold. The ending's one-line moral takes bold and underline only. Everything else stays plain.

  • **words** - bold. Use it for one phrase a screen, not a sentence.
  • __words__ - underline. Drawn in text colour so it is not mistaken for a link. Underscores inside a word (file_name) are left alone.
  • A line starting - - a bullet. Consecutive bullet lines, even with a blank line between them, make one list.
  • A line starting 1. - a numbered list. Numbering starts from the first number you write.

Option labels, keywords, model answers, trainer notes and learners' own answers stay plain. The session summary, the email message and dashboard excerpts drop the marks.

Debrief rows on any pagev0.3

Endings were the only place for revealed rows. Now any screen, consequence, notice or written card takes them too - the same [label, text] pairs, drawn the same way. Learners see them once they have acted: on a screen and a consequence, below the text; on a notice card, after Submit; on a written card, once the answer is final (it passed, or no attempts are left).

"revealed":[["What you noticed","The date on the logs, not the complaint count."]]

Any node takes a media array. Links, never embeds - the file stays small and portable.

         {"type":"video","label":"2-min setup","url":"https://..."}]

Scenes

Procedural backdrops, no art needed: stage river office data conflict team ai matrix launch storm. Unknown names fall back to stage.

What the validator checks

  • Every to, toPass, toFail resolves to a real node or ending
  • No unreachable nodes or orphan endings
  • Every rubric criterion has keywords - one without them can never be met
  • Every gated wrong answer carries a coaching note
  • Every ending has a verdict
  • sendTo is an object (v0.3)

Theme

Every exported file carries a dark and a light theme, toggled from the sun icon in the header and remembered per device. Light is a white and blue scheme for projectors and printed handouts. Scene art follows the theme automatically - it is drawn from the same tokens as the text.

Layout

The scene is a banner, capped at roughly a fifth of the viewport, so the words get the page. If you are writing long narrative text, that is the ratio to design for - do not expect the picture to carry meaning it cannot carry.

Your own picture, or none (v0.3). Any screen, consequence or ending can take "sceneImg": "https://..." (with an optional "sceneAlt") to replace the built-in art with your own image, or "scene": "none" to drop the banner. A consequence with no picture of its own uses its decision's. At scenario level, "hideArt": true removes the built-in art on every screen (your own pictures still show), and "thumbImg" replaces the card picture in the hub. Images are links, never embedded files.

The end report (v0.3). The ending screen has a folded 'See your path' diagram, and 'Save my report' downloads a page with the same diagram, then each step: the situation, what you chose, what happened, why it worked or what it cost, the stronger move where you missed it, what you noticed and missed, your written answer with what it met, and the model answer. It is built from the scenario itself - nothing extra to write.

Classroom

Each run ends with the 'Send to trainer' box and a copyable summary in plain sentences, with a compact code as the last line:

The Requirement That Wasn't - Product analysis scenario
Chose: Ask ops for a concrete case
Gap check: 3/3 of the must-haves
Written answer: 2/3 rubric criteria, short on who owns the call when it fails
Ending: Better, but still readable two ways
PUP|signoff|B>0+1+3(3/3)>written(2/3)|partial

Students send it to you or drop it in the class channel. You read decisions, not just endings, and the debrief runs off what actually happened in the room - in the Learner result tab, one learner at a time, or by reading the messages.
